# kompress_zh 集成笔记——综合评测材料：三类语义混排

本文为综合性集成笔记，刻意将"应保留"、"不应沿用"、"仍不确定"三类语义内容混排，模拟真实交接场景中信息密度较高的文档。阅读本文需要区分每条信息的实际置信程度，这正是中文压缩通道需要保住的语义精度。

## 一、集成背景与目标

`kompress_zh` 集成的目标是在 `headroom-zh` 中新增中文纯文本压缩分支，同时确保原有英文 `Kompress` 路径完全不受影响。这是一个增量集成，不是重写。

集成涵盖以下模块：
- `headroom/compress.py`：API 接口层，新增 `CompressConfig.kompress_zh_model` 字段。
- `headroom/transforms/content_router.py`：路由层，新增 `_is_chinese_dominant_text(...)`、`_get_kompress_zh(...)` 等函数。
- `headroom/transforms/kompress_zh_compressor.py`：中文压缩器实现，使用 Swift 后端。
- `pyproject.toml`：依赖项，新增 `peft>=0.11.0,<1.0` 和 `ms-swift>=4.1.3`。
- `tests/test_transforms/test_content_router.py`：路由回归测试。

## 二、已验证可信的内容（应保留类）

以下内容在 AutoDL 远程环境中经过 2026-06-14 和 2026-06-15 两天的实际验证，结论可信：

**路由分叉逻辑**：`_is_chinese_dominant_text(...)` 的判定逻辑正确区分了中英文内容，`_get_kompress_zh(...)` 在中文路径上被正确调用。验证时观察到：英文内容走原有 `_get_kompress`，中文内容走 `_get_kompress_zh`，两条路径独立运行，互不干扰。

**Swift 后端推理路径**：`language_model_only=True` 参数配合 `PeftModel.from_pretrained(...)` 和 `local_files_only=True` 的本地 snapshot 加载方式，在验证环境中产出了实际压缩文本，不是 passthrough。早期使用裸 `transformers` 加载器时存在 prompt echo 问题，当前 Swift 路径已修复该问题。

**`tool_result` 路径验证**：`ContentRouter.apply(...)` 层面，OpenAI 风格 `tool` 消息路径和 content-block `tool_result` 路径均通过验证，观察到 `router:tool_result:text` 标记正确出现。

**依赖版本约束**：`peft>=0.11.0,<1.0` 和 `ms-swift>=4.1.3` 是与训练/评测栈对齐的版本锁定，必须保留在 `pyproject.toml` 中。

## 三、不应盲目沿用的做法（不应沿用类）

**错误的 README 措辞**：曾出现过"kompress_zh 替换了 Kompress"的描述，这是错误的。两条路径并行，英文路径保持不变。在任何面向用户或团队的文档中，都不应使用暗示全量替换的措辞。

**将 smoke 脚本定性为产品代码**：`scripts/smoke_autodl_headroom.py`（含 `--expect-kompress` 变体）、远程上传脚本、AutoDL 专用辅助脚本，均是验证产物，不应作为产品资产发布。这些脚本在 AutoDL 环境之外无法运行，将其纳入产品代码只会增加维护负担，并误导对测试覆盖度的判断。

**将无关 ONNX 遗留改动混入集成提交**：legacy ONNX 导出相关的任何改动，如果没有独立的保留理由，不应混入 `kompress_zh` 集成的提交记录中。

**从 `headroom-zh-audit` 直接发布**：该工作树被大量匿名临时文件污染，直接提交会将不应入库的文件纳入仓库，应使用 `headroom-zh-publish-tmp` 工作树作为干净的发布面。

## 四、仍存在不确定性的事项（仍不确定类）

**关于"从全新机器从零复现"**：2026-06-14/15 的验证是在**已准备好的 AutoDL 环境**（存在 base model 缓存、adapter checkpoint、Python 虚拟环境）中完成的。这不代表已从一台空白机器系统性地走完了全部复现步骤。"blank AutoDL machine bootstrap"的完整可重复性，需要有人实际从冷环境再走一遍才能确认。在此之前，对"任意新机器均可直接复现"的结论应保持谨慎。

**本地 Windows pytest 的可信范围**：本地 Windows 开发机因缺少 `headroom._core` 和 `tiktoken`，完整 `pytest` 不可作为可靠质量门控。当前通过的本地测试不能替代在 AutoDL 目标环境中的验证结论。

**Windows zip 打包的反斜杠警告**：这一问题目前对 smoke 验证无害，但不是成熟工具链的理想状态。它表明跨平台打包流程存在改进空间，属于非阻塞但待处理的清理项。
