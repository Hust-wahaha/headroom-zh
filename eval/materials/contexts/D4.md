# kompress_zh 集成笔记——架构定位、发布工作树与剩余清理项

本文为集成笔记中文化版本，重点说明 `kompress_zh` 在整体架构中的定位、推荐的代码发布路径，以及当前剩余的非阻塞性清理事项。本文混排了三类语义内容，请在阅读时主动区分：哪些事项经过验证应当保留，哪些做法不应盲目沿用，哪些事项仍存在不确定性。

## 一、架构定位：两条并行路径，不是替换关系

`kompress_zh` 集成的核心架构原则是**增加中文分支，保留英文路径**，两条路径并行运行。这一点必须在所有面向外部的描述中保持一致：

- **英文或非中文主导纯文本** → 原有 `Kompress` 路径（保持不变）
- **中文主导纯文本** → 新增 `kompress_zh` 路径
- **结构化内容**（JSON/代码/日志/HTML）→ 现有 Headroom 路由，不被劫持

任何措辞上暗示"kompress_zh 取代了 Kompress"的表达，都是对架构的错误描述，不应使用。这类错误描述一旦进入 README 或设计文档，会误导后续参与者对系统行为的预期，并可能导致错误的集成决策。

## 二、应当保留的核心集成改动汇总

以下是本次集成中确认应当保留的所有关键改动（汇总自各子模块）：

**API 接口层**（`headroom/compress.py`）：
- `CompressConfig.kompress_zh_model` 字段及其透传至 `pipeline.apply(...)` 的调用链

**路由层**（`headroom/transforms/content_router.py`）：
- `_is_chinese_dominant_text(...)`、`_get_kompress_zh(...)`、`_runtime_kompress_zh_model`
- 中文感知的 `_try_ml_compressor(...)` 改动
- `_estimate_text_tokens(...)` 及调用点替换

**压缩器实现**（`headroom/transforms/kompress_zh_compressor.py`）：
- Swift 后端推理路径
- `language_model_only=True` 参数
- `PeftModel.from_pretrained(...)` 配合 `local_files_only=True` 的本地加载修复
- `get_template(..., default_system=...)` 模板初始化
- 禁用可见 thinking 输出

**依赖项**（`pyproject.toml`）：
- `peft>=0.11.0,<1.0`
- `ms-swift>=4.1.3`

**回归测试**（`tests/test_transforms/test_content_router.py`）：
- 中文主导检测器测试
- 英文路径回归测试
- 中文路径回归测试

## 三、推荐的代码发布工作树

推荐使用 `headroom-zh-publish-tmp` 作为干净的代码推广工作树（promote worktree）。理由如下：
- 该工作树仅包含相关的集成改动，边界清晰。
- `headroom-zh-audit` 工作树被大量匿名临时文件污染，不适合作为直接提交面。

不应该直接从 `headroom-zh-audit` 工作树提交代码，即便其中包含正确的集成改动。使用被污染的工作树会引入无关文件，增加代码审查的难度，并可能将不应发布的临时文件纳入仓库。

## 四、不应沿用的做法（详细说明）

### 4.1 在 README 中使用暗示"全量替换"的措辞

除了上文提到的架构定位问题之外，还需要注意：如果在 PR 描述或 commit message 中使用"重写了压缩器"、"替换了 Kompress"等措辞，即便实际代码是正确的，也会给代码审查者留下错误印象，可能导致不必要的反对或返工。

### 4.2 将一次性验证脚本定性为"测试套件"

AutoDL 专用的 smoke 验证脚本（如 `scripts/smoke_autodl_headroom.py` 和 `scripts/smoke_autodl_headroom.py --expect-kompress`）是特定环境下的一次性验证工具，不是通用自动化测试套件。在复现文档中引用它们是合适的；但将其描述为"已有充分测试覆盖"的证据，会高估当前的测试基础设施成熟度。

### 4.3 将 ONNX 导出遗留改动打包进集成提交

如果在集成开发过程中碰巧接触了 legacy ONNX 导出相关代码，这些改动应该独立提交或不提交，而不是混入 `kompress_zh` 集成的 PR 中。无关改动会模糊集成的代码审查焦点。

## 五、仍存在不确定性的剩余清理事项

### 5.1 本地 Windows 完整 pytest 不可信

本地 Windows 开发环境缺少 `headroom._core`（Rust 原生扩展）和 `tiktoken`，导致完整 `pytest` 无法在本地作为可靠的质量门控。这一状态在当前阶段属于非阻塞性限制，但需要如实记录，不应在报告或演示中回避这一事实。

### 5.2 Windows zip 打包路径的反斜杠警告

Windows 本地打包 zip 文件后，在 Linux 环境用 `unzip` 解压会产生反斜杠路径分隔符警告。当前对 smoke 验证而言是无害的，但这不是一个成熟的跨平台验证工具链应有的状态。这属于已知的待改进项，不影响当前演示路径，但应在未来的工具链改进中处理。
