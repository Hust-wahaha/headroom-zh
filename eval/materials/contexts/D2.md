# kompress_zh 集成笔记——中文压缩器实现与依赖项

本文为集成笔记中文化版本，专注于 `kompress_zh` 中文压缩器的具体实现方式、后端推理栈的选择理由、依赖项版本要求，以及各类事项的确认状态。请仔细区分"已验证应保留"、"不应沿用"与"仍不确定"三类语义。

## 一、中文压缩器实现（kompress_zh_compressor.py）

### 1.1 必须保留的实现细节

在 `headroom/transforms/kompress_zh_compressor.py` 中，以下实现细节必须保留：

**Swift 后端推理路径**：中文压缩器使用 Swift 后端（ms-swift 框架）进行推理。更早版本曾尝试裸 `transformers` 加载器，但该方案存在严重问题——会产生 prompt echo（提示词被原样回显）和 passthrough（压缩结果直接透传而不压缩），这两种现象都会让压缩测试看起来像是路由或压缩失败，实际上是加载器选择错误。Swift 路径是唯一在实际训练/评测栈上得到验证的推理方式。

**`language_model_only=True` 参数**：在 Swift 推理调用中，必须传入 `language_model_only=True`。去掉这个参数会影响模型的推理行为，产生与训练时不一致的输出格式。

**`PeftModel.from_pretrained(...)`**：LoRA adapter 的加载必须通过 `PeftModel.from_pretrained(...)` 完成。但需注意一个已知坑点：即使 adapter 文件已在本地缓存中存在，`from_pretrained` 仍可能触发 HuggingFace 元数据网络请求。在 AutoDL 代理运行时环境中，若该请求失败，系统会静默回退到 passthrough 模式，表现类似路由失败。当前修复方案是：先将 adapter 解析为本地 snapshot，再加以 `local_files_only=True` 标志加载。

**`get_template(..., default_system=...)` 调用**：模板初始化时必须传入 `default_system` 参数，确保系统提示由模板携带，请求中仅发送用户消息，与项目评测路径的期望输入格式对齐。

**禁用可见 thinking 输出**：如果模型支持 thinking/reasoning 模式，必须在推理调用中禁用可见 thinking 输出，否则输出中会混入思考过程，干扰后续 token 节省量的统计。

### 1.2 请求格式的重要性

模板携带系统提示、请求只发用户消息这一格式，是与训练/评测栈对齐的关键细节。如果修改这个格式，压缩器的输出行为可能与评测预期不符，导致评测结果失去参照意义。

## 二、依赖项版本要求

在 `pyproject.toml` 中，以下依赖项版本约束必须保留：

```
peft>=0.11.0,<1.0
ms-swift>=4.1.3
```

**保留理由**：`kompress_zh` 现在依赖与训练和评测项目相同的推理栈。如果放宽这些版本约束，可能引入与训练时环境不兼容的行为差异。特别是 `peft>=0.11.0,<1.0` 的上界限制是有意为之，防止未来 peft 1.x 的破坏性变更静默影响中文压缩器行为。

## 三、不应沿用的做法

### 3.1 将验证期间产生的临时脚本提升为产品代码

集成验证期间产生的 AutoDL 专用脚本（包括远程上传脚本、一次性 smoke 套件、AutoDL 专用验证辅助脚本）是验证产物，不是用户面向的仓库资产。将它们包含进正式产品代码发布，会混淆仓库中什么是"产品"什么是"验证工具"的边界，增加后续维护负担。

### 3.2 将无关的遗留 ONNX 导出改动混入本次集成

如果在集成 `kompress_zh` 期间碰巧也修改了 legacy ONNX 导出相关脚本，这些改动不应作为 `kompress_zh` 集成的一部分提交，除非有独立充分的理由。混入无关改动会模糊集成的边界，使代码审查和回归排查更困难。

## 四、仍存在不确定性的事项

### 4.1 `kompress_zh` 仅在 AutoDL 环境中经过验证，未从全新机器从零完整复现

集成验证于 2026-06-14 至 2026-06-15 在 AutoDL 远程环境中完成，确认了：英文路由独立运行正常、中文路由产出实际压缩文本、`tool_result` 路径通过。然而，这一验证基于**已准备好的 AutoDL 环境**（存在真实的 base model 缓存和 adapter checkpoint），并不代表任何一台全新的空白机器都能不经额外环境准备就复现同样结果。这一区分非常重要：在已验证环境中表现正常，不等同于"从零复现路径已完全确定"。

### 4.2 本地 Windows 环境 pytest 不可信

如前所述，本地 Windows 机器上缺少 `headroom._core` 和 `tiktoken`，导致完整 `pytest` 无法作为可靠的质量门控使用。这不是集成本身的缺陷，而是开发环境局限性的诚实描述。
