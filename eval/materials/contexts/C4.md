headroom-zh 灰度发布操作规程（v0.8.2 升级至 v0.8.3，生产集群 prod-cluster-cn）

本规程面向负责生产集群升级的运维工程师，描述将 headroom-zh 服务从版本 v0.8.2 滚动升级至 v0.8.3 的完整操作流程，共七个步骤。升级过程中需保持服务对外持续可用，因此各步骤的执行顺序和关键检查点须严格遵守，不得跳过任何验证环节。

操作步骤一：备份当前生产配置

执行命令：ssh headroom@prod-gw-01 "tar -czf /backup/headroom-zh-conf-$(date +%Y%m%d%H%M%S).tar.gz /etc/headroom-zh/ /root/.config/headroom-zh/"

在进行任何变更之前，必须首先完成当前配置的备份。备份文件将以含时间戳的文件名写入 prod-gw-01 节点的 /backup/ 目录。备份完成后须确认文件大小大于 0 字节；若 tar 命令报错或生成文件为空，说明配置目录可能存在问题，须立即中止升级排查原因，不可跳过本步骤直接执行后续操作。

操作步骤二：在金丝雀节点拉取新版本镜像

执行命令：ssh headroom@prod-node-01 "docker pull registry.internal.example.com/headroom-zh:v0.8.3 && docker image inspect registry.internal.example.com/headroom-zh:v0.8.3 --format '{{.Id}}'"

金丝雀节点 prod-node-01 是集群中最先接收升级的节点，当前承载约 5% 的线上流量。docker image inspect 命令用于确认镜像已完整拉取并输出镜像摘要 ID；若输出为空或 pull 命令失败，须检查镜像仓库 registry.internal.example.com 的连通性，镜像确认成功后方可继续执行步骤三。本步骤依赖步骤一的备份已完成。

操作步骤三：在金丝雀节点停止旧容器并启动新版本

执行命令：ssh headroom@prod-node-01 "docker stop headroom-zh-prod && docker rm headroom-zh-prod && docker run -d --name headroom-zh-prod --restart always -p 9087:9087 -v /root/.config/headroom-zh:/config:ro -e HEADROOM_CONFIG_DIR=/config registry.internal.example.com/headroom-zh:v0.8.3"

停止旧版本容器后新容器立即拉起，中间停机窗口约 10 至 15 秒，流量路由器在此期间自动将请求切换至集群其余节点，不影响整体服务可用性。新容器启动后须等待约二十秒完成初始化，再执行步骤四的健康检查。若新容器在六十秒内自行退出（docker ps 显示 STATUS 为 Exited），须立即回滚至 v0.8.2 镜像，禁止继续推进升级流程。

操作步骤四：对金丝雀节点执行健康检查（Level 1 验证）

执行命令：bash /opt/headroom-zh/scripts/healthcheck.sh --host prod-node-01 --port 9087 --retries 5 --interval 10

脚本向 http://prod-node-01:9087/health 连续发送五次 HTTP GET 请求，每次间隔十秒。全部五次请求均返回 HTTP 200 且响应体包含 "status":"ok" 字段时，视为健康检查通过，脚本退出码为 0。若任意一次请求失败或退出码非 0，禁止继续执行步骤五，须立即在 prod-node-01 上回滚至 v0.8.2 镜像，并将故障详情记录至升级日志 /var/log/headroom-zh/upgrade_log_20260622.txt。只有本步骤以退出码 0 通过，才能继续对集群其余节点执行滚动升级。

操作步骤五：滚动升级集群其余节点

执行命令：bash /opt/headroom-zh/scripts/rolling_upgrade.sh --nodes prod-node-02,prod-node-03,prod-node-04,prod-node-05,prod-node-06,prod-node-07,prod-node-08 --image registry.internal.example.com/headroom-zh:v0.8.3 --port 9087 --batch-size 2

脚本每批次同时升级两个节点，每批完成后自动执行与步骤四相同逻辑的健康检查，检查通过后继续执行下一批次，若任一节点健康检查失败则脚本暂停并输出告警，等待运维人员决策（继续升级或触发全集群回滚）。本步骤须在步骤四通过后方可执行，执行期间不得手动干预节点的容器状态。

操作步骤六：全集群 Level 2 功能验证

执行命令：bash /opt/headroom-zh/scripts/run_smoke_tests.sh --level 2 --cluster prod-cluster-cn --port 9087

脚本向集群 prod-cluster-cn 所有节点发送中文压缩功能的端到端测试请求，验证 v0.8.3 版本新压缩算法的输出与基准结果的相似度是否不低于 0.85（基于 Jaccard 相似度计算）。测试报告将写入 /var/log/headroom-zh/smoke_level2_upgrade_20260622.json。若全集群 Level 2 验证通过（脚本退出码为 0），方可执行步骤七。若测试失败，须评估实际影响范围后决定是否触发全集群回滚。

操作步骤七：写入升级记录并通知相关团队

执行命令：python /opt/headroom-zh/scripts/post_upgrade_notify.py --version v0.8.3 --cluster prod-cluster-cn --report /var/log/headroom-zh/smoke_level2_upgrade_20260622.json --notify-channel ops-alert

脚本将升级结果（包括版本号、升级完成时间、Level 2 验证分数等关键信息）写入升级记录文件 /var/log/headroom-zh/upgrade_log_20260622.txt，并通过内部通知渠道 ops-alert 推送升级完成消息给相关团队。本步骤为整个升级流程的收尾环节，须在步骤六通过后执行。若步骤六 Level 2 验证失败但团队决策保留新版本，仍须执行本步骤完成记录，并在通知中明确注明 Level 2 验证结论及团队决策依据。
