## 0. 前提与范围

**要排查的问题**：`kompress_zh`（中文压缩通道）在**离线**能正常压缩，但在**实时 `headroom wrap codex`（经本地 proxy）** 场景下不压缩中文——dashboard 长期只显示 ~1.3% 节省（实为 `tool_schema_compaction` 固定省 109，kompress_zh 贡献为 0）。

**已确立的基准（作为对照，不再重复验证）**：

| 基准 | 状态 | 用途 |
|---|---|---|
| kompress_zh **本体能力** | 已证实：离线 harness 38.5% 节省 @ 95% 正确率；单样本 1647→315 省 81% | 证明「模型/算法本身没问题」，排查时**不要再怀疑算法** |
| **离线**同步脚本压缩 | 已证实可压（直接 `import` 调用，主线程同步） | 作为「正常路径」对照基准 |
| **AutoDL（Linux + 4090）实时 proxy** | 已证实可压（dashboard 48.9%） | 作为「同一条 proxy 路径在另一环境跑通」的对照基准 |
| 本机 **Windows 11 + RTX 4060 Laptop（8GB）实时 proxy** | **失效（本文要排查的对象）** | 排查目标 |

**范围边界**：
- **只查实时 proxy 路径**。kompress_zh 本体、离线 harness、AutoDL 均作为**对照基准**，不在排查范围内重新验证。
- 本机环境层已修复（见 §1～§7 修复记录）：torch `cu128` 可用、`is_kompress_zh_available() == True`、editable 挂载正确。因此**环境是否可用**不再是未知量，但仍作为排查链的第一道闸（H1）以防回归。

**关键命令约定（zh 版，本机）**：
- venv python：`<repo>\.venv\Scripts\python.exe`（下文简写 `PY`）
- CLI 入口：激活 `.venv` 后用 `headroom`（实为手写转发的 `headroom.cmd` → `python -m headroom.cli`，见 §9.2）
- proxy 日志：`C:\Users\yanyi\.headroom\logs\proxy.log`
- wire-debug 抓包目录：`<repo>\eval_docs\_wire_debug`
- proxy 端口：`8787`（`wrap` 见端口被占就**复用**，故每次实验前必须清端口）

```powershell

Get-NetTCPConnection -LocalPort 8787 -State Listen -EA SilentlyContinue |
  ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
```

## 1. 排查顺序总览（决策流程 · 这是审查重点）

排查按 **「先廉价、先排除根基性因素 → 再查路由 → 最后查执行环境/线程/框架隔离」** 的**依赖顺序**编排。
核心原则：**靠后的假设只有在靠前的根基成立时才有意义**，所以先把根基钉死，避免后面被干扰、误判。

```
[阶段 A · 根基：跑的是不是对的、能不能压] —— 廉价、先排除，否则后面全无意义
  H1  跑着的 proxy 是不是含 kompress_zh 的 zh 版？torch 是否真可用？
        │  └─ 若跑的是上游全局版 / torch 坏 → 后面所有路由/线程实验都是空中楼阁，先修这个
  H6 的"前置子项" 启动是否预加载了 kompress_zh？（影响"首次 vs warm"判读，先确认以免误读超时）
        ▼ 根基 OK（zh proxy + torch 可用）后才继续
[阶段 B · 路由：中文内容到底有没有走到 kompress_zh] —— 中等成本，排除"压根没送/没路由"
  H4  codex 有没有把中文文件作为 function_call_output 送进来？（抓包）
  H3  Responses 路径是否真把 function_call_output 路由进压缩管线？（看 PERF/transforms）
  H5  是否被尺寸上限 / skip 集 / 缓存 / analysis-protect 跳过？
        │  └─ 若内容根本没送/没路由 → 不是执行问题，是路由问题，到此即可定位
        ▼ 确认"内容确实送进来且确实路由到 kompress_zh"后才继续
[阶段 C · 执行：路由到了，但压不出来] —— 最贵、最深，区分"超时 vs 卡死 vs 框架隔离"
  H6  是不是 30s 压缩超时？（首次懒加载 + 推理 > 30s）—— 区分"慢但能完成" vs "卡死"
  H7  块太大导致即使预热也超时？（尺寸—耗时关系）
  H2  dashboard % 是否被 codex 巨大上下文稀释？（分母核账，辅助判读，不是主因）
  H8  多进程抢 GPU 卡死？（单进程对照排除环境噪声）
  H9  kompress_zh 在 proxy 工作线程（executor）里跑会卡死（线程不安全 / CUDA 上下文）
  H10 ms-swift Swift 推理引擎未被干净隔离进 proxy（沿用原生路径 vs Transform 反复调）
  H11 Swift 引擎对执行上下文有隐含假设（主线程/单进程/自管 CUDA stream）被 proxy 破坏
```

**为什么这个顺序合理**：
1. **H1 必须最先**：若跑的根本不是含 kompress_zh 的 zh proxy、或 torch 坏掉，那么「不压缩」是必然且无信息量的——后面任何路由/线程实验的输入都被污染。这是最廉价（查个进程+一行 import）也最根基的一道闸。
2. **路由（H3/H4/H5）必须在执行（H6+）之前**：若中文内容压根没被送进来或没被路由到 kompress_zh，那讨论「线程是否卡死」毫无意义——根本没进到那一步。先用抓包+日志确认「内容已送达且已路由」，把问题域从「整条链」收敛到「最后一步：执行」。
3. **执行层内部也有顺序**：先用最直接的现象（proxy.log 的超时/放行日志，H6）区分**「超时但线程能跑完（慢）」**还是**「线程卡死永不返回」**；再用尺寸—耗时关系（H7）和分母核账（H2）排除「只是慢/被稀释」的良性解释；再用**单进程对照（H8）**排除多进程争用这个环境噪声；最后才落到最深、最难证的**线程/框架隔离（H9/H10/H11）**——因为这三者改起来最贵，必须在前面所有良性解释都被排除后才下此结论。
4. **「先排除良性解释、再下昂贵结论」**：H2/H7/H8 本质是「把容易的、便宜的解释先排掉」，确保不会把一个其实是「超时配置」或「多进程噪声」的问题误判成需要重构 proxy 集成的「框架隔离」问题。

## 2. 阶段 A · 根基

### H1 — 跑着的是否为含 kompress_zh 的 zh 版 proxy，且 torch 真可用？

**假设描述**：8787 端口上常驻的 proxy 实际是**全局上游版**（`uv\tools\headroom-ai`，不含 `kompress_zh_compressor.py`、且其 torch 在本机 c10.dll 1114 坏掉），`wrap` 复用了它 → 中文压根压不了。（对应 §10 H1）

**排查方式（步骤）**：
1. 查谁占着 8787，定位其可执行/工作目录：
   ```powershell
   $c = Get-NetTCPConnection -LocalPort 8787 -State Listen -EA SilentlyContinue
   $c | ForEach-Object { Get-Process -Id $_.OwningProcess | Select-Object Id, Path, StartTime }
   # 关注 Path：应指向 ...\headroom_zh_eval\headroom-zh\.venv\Scripts\python.exe
   # 若指向 ...\uv\tools\headroom-ai\... 则是上游全局版（坏）
   ```
2. 该 proxy 用的 python 是否含 kompress_zh、torch 是否可用（用与 proxy 同一个解释器）：
   ```powershell
   $env:HF_ENDPOINT="https://huggingface.co"
   & "<repo>\.venv\Scripts\python.exe" -c "import torch; print('cuda', torch.cuda.is_available()); from headroom.transforms.kompress_zh_compressor import is_kompress_zh_available; print('zh_avail', is_kompress_zh_available())"
   ```
3. 看 proxy.log 启动段是否有 `c10.dll` / `WinError 1114` / `ImportError`：
   ```powershell
   Select-String -Path "C:\Users\yanyi\.headroom\logs\proxy.log" -Pattern "1114|c10\.dll|ImportError|is_kompress_zh_available|kompress_zh" | Select-Object -Last 30
   ```

**预期结果与判读**：
- 若步骤 1 Path 指向 `uv\tools\headroom-ai`，或步骤 2 任一为 `False`/抛 `OSError`，或步骤 3 出现 1114 → **证实 H1**：跑的不是健康的 zh proxy，先卸载全局版/清端口/用 zh venv 重启（§9.1），再继续后续排查。
- 若 Path 指向 zh `.venv`、`cuda=True`、`zh_avail=True`、日志无 1114 → **排除 H1**，根基健康，进入阶段 B。

> 排查结果（2026-06-27 实测）：当前无 proxy 常驻 8787（干净）。直接核验 zh venv：`torch 2.11.0+cu128`、`torch.cuda.is_available()=True`、设备 `NVIDIA GeForce RTX 4060 Laptop GPU`、`is_kompress_zh_available()=True`。子模块 HEAD=8c60312、工作区干净。
> 结论：[ ] 证实  [x] 排除  [ ] 部分  —— 依据：venv 健康，根基这道回归闸通过；进入后续排查。

### H6-pre — 启动时是否预加载了 kompress_zh（影响"首次 vs warm"判读的前置项）

**假设描述**：`eager_load_compressors()` 只预加载英文 Kompress(ONNX)，**不预加载 kompress_zh**；若未打预加载补丁，则「首个中文块必含 ~15-25s 模型加载」，会把后面 H6 的超时判读带偏。先确认**本机 fork 是否真在 `eager_load_compressors`（`content_router.py:1655` 起的函数体）内加了 kompress_zh 预加载分支**，作为后续判读的已知量。（对应 §10 H6 的前置子项 / 改进建议 #6）

**排查方式（步骤）**：
1. 确认补丁**确实加在 `eager_load_compressors` 函数体内**（不能只看文件里有没有 `kompress_zh` 字样——别处也有；要确认它在该函数的预加载分支里）：
   ```powershell
   # 先定位函数所在行
   Select-String -Path "<repo>\headroom\transforms\content_router.py" -Pattern "def eager_load_compressors"
   ```
   再用 Read 打开 `content_router.py` 第 1655 行起的函数体（约 40 行），**确认其中有 kompress_zh 的预加载/构建引擎分支**（例如调用 `KompressZhCompressor(...).compress(...)` 或 `_get_engine(...)` 触发加载）。仅 grep 字样不足以判定，必须读函数体。
2. 看 proxy.log 启动段是否打印了 kompress_zh 预加载/模型加载日志（启动多花 ~25s）：
   ```powershell
   Select-String -Path "C:\Users\yanyi\.headroom\logs\proxy.log" -Pattern "eager|preload|kompress_zh.*load|adapter|TransformersEngine" | Select-Object -Last 20
   ```

**预期结果与判读**：
- 若补丁在位且启动日志含 kompress_zh 加载 → 预加载**已生效**：后续 H6 中观察到的耗时应视为**纯推理时间**（不含加载）。
- 若无预加载 → 后续 H6 第一个中文块的耗时**含一次性加载**，判读 H6/H7 时必须区分「首次（含加载）」与「warm（纯推理）」，否则会把加载耗时误算成推理超时。

> 排查结果（2026-06-27 实测）：读 `content_router.py:1655` 起的 `eager_load_compressors` 完整函数体——其中**只预加载** ①英文 Kompress(ONNX) ②Magika ③CodeAware/tree-sitter ④SmartCrusher，**没有任何 kompress_zh 预加载分支**。子模块工作区干净（HEAD=8c60312），即 §9.4 声称"已应用的预加载补丁"在当前子模块里**实际不存在**（疑在子模块提交/重置时丢失）。kompress_zh 仅在 `_get_kompress_zh()`(1777) 懒加载、由路由(1522) 首次命中时触发。
> 结论：[ ] 预加载已生效  [x] 未预加载（判读须区分首次/warm）  —— 依据：函数体无 kompress_zh 分支 → **每个新起的 proxy 首个中文块必含 ~20-25s 一次性加载**，这是下面 H6 冷加载超时的前提。

## 3. 阶段 B · 路由

### H4 — codex 是否把中文文件作为可压缩的 tool output 送进来？（抓包）

**假设描述**：codex 没把读到的文件作为 `function_call_output` 送进 proxy（或内容被它自己缓存），所以 proxy 无内容可压。（对应 §10 H4）

**排查方式（步骤）**：
1. **先开启 wire-debug 抓包**（proxy 默认不写线缆抓包，必须显式打开）。在启动 proxy 的同一 shell 里设环境变量后再起 proxy：
   ```powershell
   # 抓包写入目录（与本文档约定一致），并开启 wire-debug
   $env:HEADROOM_WIRE_DEBUG = "1"
   $env:HEADROOM_WIRE_DEBUG_DIR = "<repo>\eval_docs\_wire_debug"
   # 注：变量名以本机 fork 实际为准——若上面不生效，先 grep 源码确认开关名：
   #   Select-String -Path "f:\...\headroom-zh\headroom\proxy\*.py" -Pattern "WIRE_DEBUG|wire_debug|getenv.*WIRE"
   # 然后清端口、重启 proxy（headroom wrap codex）
   ```
2. 触发一次「让 codex 读一个大中文文件」的对话，让其产生 `function_call_output`。
3. **先列出目录里真实的抓包文件名**（不要直接拍脑袋写 `-Filter`，命名规则因 fork 而异，写错 `-Filter` 会 0 命中、卡住）：
   ```powershell
   $dir = "<repo>\eval_docs\_wire_debug"
   Get-ChildItem $dir | Sort-Object LastWriteTime | Select-Object -Last 20 Name
   # 观察真实命名（如本机历史抓包形如 *_ws_inbound_client_frame.json），据此再定 -Filter
   ```
4. 在 inbound 帧（codex → proxy 方向，文件名含 `inbound`）里找工具输出：
   ```powershell
   # -Filter 用上一步看到的真实命名片段；先确认有命中再统计
   $hits = Get-ChildItem $dir | Where-Object { $_.Name -match "inbound" }
   $hits | ForEach-Object { $_.Name; (Select-String -Path $_.FullName -Pattern "function_call_output|local_shell_call_output").Count }
   ```
5. 统计命中帧里中文工具输出的字数量级（应是几千字，与离线样本同量级）。

**预期结果与判读**：
- 若抓到 inbound 帧含 `function_call_output` 且其中是几千字中文（如 §10 记录的 9090 字）→ **排除 H4**：内容确实送进来了，问题不在「没送」。
- 若所有 inbound 帧都无 `function_call_output`，或中文内容不在 input items 里（被 codex 缓存/省略）→ **证实 H4**：codex 侧没把可压内容送来，需从 codex 工具调用/缓存行为入手，与 proxy 压缩无关。

### H3 — Responses 路径是否真的把 function_call_output 路由进 kompress_zh？

**假设描述**：Responses API 路径**完全不路由**中文内容，只压 tool schema（`transforms=tool_schema_compaction`、`msgs=0`）。（对应 §10 H3）

**排查方式（步骤）**：
1. 在同一次「读大中文文件」的请求后，看 proxy.log 的 `PERF` 行：
   ```powershell
   Select-String -Path "C:\Users\yanyi\.headroom\logs\proxy.log" -Pattern "PERF|transforms=|msgs=" | Select-Object -Last 40
   ```
2. 关注两类帧：
   - codex **读文件之前**的帧：通常 `msgs=0`、`transforms=tool_schema_compaction`（无工具输出）；
   - codex **读完文件、把 `function_call_output` 回送**的那一帧：应出现 kompress_zh 相关 transform 或对该工具输出的处理。
3. 核对源码路由逻辑：Responses 路径只压 `function_call_output` / `local_shell_call_output` 等「工具输出」，不压 user/system（保护 prefix 缓存）——确认看的是对的那一帧。

**预期结果与判读**：
- 若仅凭「读文件前」的帧看到 `msgs=0` 就判定不路由 → 这是**误判**（§10 已记录此坑）。必须找**读完文件回送 function_call_output 的那一帧**。
- 若回送帧里 kompress_zh 参与了路由（transform 列表含中文压缩 / 该 tool output 进入压缩管线）→ **排除 H3**：路由是通的，问题在执行层。
- 若回送帧确实存在工具输出、但 transform 里始终没有 kompress_zh、内容也未进压缩管线 → **证实 H3**：路由分支漏判，需查 Responses handler 的路由条件。

## 4. 阶段 C · 执行

> 阶段 C 的总目标：在「内容已送达且已路由到 kompress_zh」（阶段 B 确认）的前提下，
> 弄清**为什么压不出来**——区分四种性质截然不同的情况：
> **(a) 慢但能完成（超时配置问题）/ (b) 块太大注定超时 / (c) 多进程噪声 / (d) 线程或框架隔离导致的"卡死"**。

### H6 — 是否是 30s 压缩超时？区分「超时放行 vs 真压缩 vs 卡死」

**假设描述**：`COMPRESSION_TIMEOUT_SECONDS = 30`（硬编码，见 `headroom/proxy/helpers.py:770`），压缩被 `asyncio.wait_for(..., timeout=30)` 包裹（`openai.py:1324/1711/1735`）。首次懒加载 + 推理 > 30s → 超时 → 原样转发。（对应 §10 H6）

**关键判读维度**：要分清的三种结局，靠**两条不同的日志行 + `/stats`** 联合判定，**不要把它们当成同一行逐字匹配**：
- **超时放行行**（独立日志，**不含 opt_ms**）：`[{request_id}] WS /v1/responses frame compression failed; forwarding original: TimeoutError: ...`（源码 `openai.py:4513-4519`）。
- **PERF 行**（另一条独立日志，**只有这里有 opt_ms 与 tok_***）：`[{request_id}] PERF ... tok_before=N tok_after=N tok_saved=N ... opt_ms=N`（源码 `openai.py:4865-4873`、`outcome.py:389-395`）。
- **两条行靠同一个 `[request_id]` 关联**——一次请求会有 PERF 行；若该请求压缩超时，则同 request_id 还会有一条 forwarding-original 行。
- **关键陷阱（P5）**：executor 线程超时后**无法被抢占**（见 H9 / `server.py` docstring），所以**无论"慢但能跑完"还是"真卡死"，asyncio 侧都在超时点解除等待、`opt_ms` 都会≈超时值（≈30000）**。因此**单看 `opt_ms≈30000` 无法区分"超时(慢)"与"卡死"**——必须叠加 `/stats` 的 `leaked_threads_total` 走势 + 调大超时复测（见判读）。

三种结局：
- **真压缩成功**：有 PERF 行且 `tok_after < tok_before`、`tok_saved>0`、`opt_ms < 30000`，**无** forwarding-original 行。
- **超时放行**：有 forwarding-original 行（TimeoutError），同 request_id 的 PERF 行 `opt_ms≈30000`、`tok_saved=0`。
- **卡死 vs 慢**：两者 `opt_ms` 都≈30000，**不能只凭 opt_ms 区分**——见下方复合判据。

**排查方式（步骤）**：
1. 确认超时常量与包裹位置（已核对，供复查）：
   ```powershell
   Select-String -Path "<repo>\headroom\proxy\helpers.py" -Pattern "COMPRESSION_TIMEOUT_SECONDS"
   Select-String -Path "<repo>\headroom\proxy\handlers\openai.py" -Pattern "COMPRESSION_TIMEOUT_SECONDS|forwarding original|opt_ms"
   ```
2. 触发一次中文压缩后，**分别 grep 两类行**（它们不在同一行），再靠 `[request_id]` 关联：
   ```powershell
   $log = "C:\Users\yanyi\.headroom\logs\proxy.log"
   # (a) 超时放行行（不含 opt_ms）
   Select-String -Path $log -Pattern "frame compression failed; forwarding original" | Select-Object -Last 10
   # (b) PERF 行（含 opt_ms / tok_before / tok_after / tok_saved）
   Select-String -Path $log -Pattern "PERF.*opt_ms" | Select-Object -Last 10
   # 取上面任一行里的 [xxxx] request_id，回查另一类行同一 id 的记录
   ```
3. 读 `/stats` 的泄漏线程计数（注意：嵌套在 `compression_executor` 下，字段名见 H9）：
   ```powershell
   (Invoke-RestMethod http://127.0.0.1:8787/stats).compression_executor |
     Select-Object leaked_threads_total, in_flight, in_flight_max, queued, queued_max
   ```
4. 临时把超时调大复测，区分「慢但能完成」与「永不完成」：若超时可配（改进建议 #6 要求改为环境变量），设较大值（如 `HEADROOM_COMPRESSION_TIMEOUT_SECONDS=90`）重启复测；若仍硬编码，需在 fork 临时改 `helpers.py:770` 后重启。

**预期结果与判读**：
- 有 PERF 行 `opt_ms<30000` + `tok_saved>0`、无 forwarding-original 行 → 中文压缩**已生效**，问题或在别处（回看 H2 稀释）。
- 有 forwarding-original(TimeoutError) + PERF `opt_ms≈30000`、`tok_saved=0`，**且把超时调到 90s 后能压成**（出现 `opt_ms` 在 30000~90000 之间且 `tok_saved>0`）→ 是**纯超时（慢但能完成）**：缩小 `HEADROOM_KOMPRESS_ZH_MAX_NEW_TOKENS`（如 256）或提高超时即可，落到 H7。
- **卡死（复合判据，三者同时满足）**：① PERF `opt_ms` 顶满超时；**且** ② `/stats.compression_executor.leaked_threads_total` 随每次请求**单调上涨、永不回落**（线程超时后仍在跑、永不返回）；**且** ③ 把超时调到 90s **仍不完成**（离线同块只需几秒）。三者齐备 → 不是「慢」是「卡死」，转 H9/H10/H11。仅满足 ① 不足以判卡死。

> 排查结果（2026-06-27 离线实测，2528 字块 @256 预算）：用**忠实复现 proxy 异步路径**的脚本（asyncio 事件循环 + ThreadPoolExecutor + `loop.run_in_executor` + `asyncio.wait_for(timeout=90)`，照搬 `server.py:725 _run_compression_in_executor`）连压三次：
> - **COLD-1st（引擎在 executor 线程内冷加载+推理）= 33.4s** → **超过硬编码 30s 超时** → 真实 proxy 在此会 `forwarding original: TimeoutError`、`opt_ms≈30000`、`tok_saved=0`。
> - **WARM-2nd = 13.8s、WARM-3rd = 14.1s** → 均 <30s，会真压成（`tok_saved>0`）。
> - **全程无卡死**（与 H9 一致）。
> 结论：[ ] 真压缩  [x] 超时放行（首次冷加载所致，预加载/调超时/调预算可解）  [ ] 卡死  —— 依据：冷加载首块顶满超时、warm 块远低于超时；**本机失效的直接现象是「首块冷加载超时」，不是卡死**。注：仍需实时 proxy+codex 端到端复测确认（见阶段B/C 待办）。

### H9 — kompress_zh 在 proxy 工作线程（executor）里跑会卡死

**假设描述**：GPU 模型在 proxy 的**非主线程/异步 executor**里跑会卡死（线程不安全 / CUDA 上下文问题）。代码证据：压缩经 `self._run_compression_in_executor(fn, timeout=...)`（`openai.py:1701/1725`）丢到独立线程池执行；`server.py:725` 的 docstring 明言「`wait_for` 超时只取消 asyncio future，**底层 executor 线程无法被抢占、会继续跑到完成或永不返回**」，并以内部计数器统计这种「泄漏线程」（在 `/stats` 里暴露为 `compression_executor.leaked_threads_total`）。这正好解释「超时放行后体感无等待，但线程其实卡死」。（对应 §10 H9）

**核心证据点**：2528 字中文块离线仅 ~8s，但在 proxy 里也卡满超时——**远超正常耗时 = 卡死，而非慢**。

**关键对照实验：主线程 vs 后台线程压同一中文块（三分支，变量已控制）**

变量控制要点：① **预热对齐**——A、B、B' 各自**正式计时前都先预热一次**，避免 A 先触发引擎加载、B 白捡缓存的不公平；② **引擎构建线程归属**——`_get_engine` 用 `_engine_lock`+`_engine_cache` 跨线程共享，若 A 先在主线程构建、B 只是复用主线程实例，就**测不到** H11 关心的「换线程构建+调用」。故新增 **B' 分支**：先 `unload_kompress_zh_model()` 清缓存，再**在后台线程内部首次构建+调用**，才真正复现 proxy 的「executor 线程内构建引擎」路径。
```powershell
$env:HF_ENDPOINT="https://huggingface.co"
& "<repo>\.venv\Scripts\python.exe" - <<'PY'
import time, threading
from headroom.transforms.kompress_zh_compressor import KompressZhCompressor, unload_kompress_zh_model
c = KompressZhCompressor()
text = open(r"<repo>\eval\materials\contexts\A4.md", encoding="utf-8").read()[:2528]

# A) 主线程压（贴合离线/AutoDL 原生路径）—— 先预热再计时
c.compress(text[:200])                 # 预热：主线程内构建引擎、填 _engine_cache
t=time.time(); c.compress(text); print("A main-thread elapsed", round(time.time()-t,1))

# B) 后台线程压（复用 A 已构建的引擎实例）—— 已预热（共享缓存）
def work_b():
    s=time.time(); c.compress(text); print("B bg-thread(reuse-engine) elapsed", round(time.time()-s,1))
tb=threading.Thread(target=work_b); tb.start(); tb.join(timeout=90)
print("B finished?", not tb.is_alive())

# B') 清缓存后，在后台线程内部首次构建+调用引擎（真正复现 proxy 的 executor-内-构建路径）
unload_kompress_zh_model()             # 清 _engine_cache，强制下次在调用线程内重建
def work_bp():
    c.compress(text[:200])             # 预热也发生在后台线程内（引擎在此线程构建）
    s=time.time(); c.compress(text); print("B' bg-thread(build-in-thread) elapsed", round(time.time()-s,1))
tbp=threading.Thread(target=work_bp); tbp.start(); tbp.join(timeout=90)
print("B' finished?", not tbp.is_alive())
PY
```
（同时观察 proxy 实际运行时 `/stats` 的泄漏线程计数——注意嵌套在 `compression_executor` 对象下、字段名为 `leaked_threads_total`：）
```powershell
(Invoke-RestMethod http://127.0.0.1:8787/stats).compression_executor |
  Select-Object leaked_threads_total, in_flight, in_flight_max, queued, queued_max
```

**预期结果与判读**：
- 若 **A 主线程几秒压完，而 B' 在后台线程内构建+调用时 90s 仍 `is_alive()`（卡死）** → **强证实 H9**：同一引擎同一块，仅因「在后台线程构建+跑」就卡死 → 线程安全/CUDA 上下文是直接根因。proxy 里 `compression_executor.leaked_threads_total` 应同步上涨佐证。
- 若 A 正常、B（复用主线程引擎）正常、唯独 B'（线程内构建）卡死 → 进一步指向 H11：问题在「引擎构建/上下文绑定到了错误的线程」，而非单纯「调用在别的线程」。
- 若 A、B、B' 都在几秒内压完 → **排除 H9**（裸后台线程不复现），卡死另有原因（可能是 proxy 的 asyncio 事件循环 + executor 组合特有，需缩小到 H10/H11 的框架隔离）。
- 若都慢但都能完成 → 不是卡死是慢，回到 H7/H6 的超时旋钮。

> 排查结果（2026-06-27 离线实测，2528 字块 @256 预算，A4 等素材拼接）：**三分支全部 ~14s 完成，无一卡死**：
> - A 主线程 = 14.1s（saved 1924, ratio 0.181）
> - B 后台线程**复用**主线程引擎 = 14.2s
> - B' 清缓存后**在后台线程内部首次构建引擎+推理** = 14.5s（warm 12.5s）
>
> 进一步用**忠实复现 proxy 异步路径**的脚本（asyncio loop + ThreadPoolExecutor + `run_in_executor`+`wait_for`，见 H6 结果）也无卡死。**裸后台线程、线程内构建引擎、proxy 同款 asyncio+executor 组合——三种都跑得好好的。**
> 结论：[ ] 证实  [x] 排除  [ ] 部分  —— 依据：卡死现象在本机**完全不可复现**。§10「最可能根因=线程卡死(H9/H11)」**判断有误**，应推翻；真正现象是 H6 首次冷加载超时。

### H10 — ms-swift 的 Swift 推理引擎未被干净「隔离」进 proxy

**假设描述**：AutoDL 跑通是因为「直接用 ms-swift 那个 Swift 框架、没把它独立出来整」；而 headroom 把它「独立」成 proxy 的一个 `Transform`、在 executor 线程里**按请求反复调用** `TransformersEngine`（`kompress_zh_compressor.py:146` 构建），偏离了 Swift 引擎被验证的原生执行上下文 → 适配性差、卡死。（对应 §10 H10，是 H9 的根因层面）

**排查方式（步骤）**：
1. 定位引擎构建点与调用频次——确认每次压缩是否复用同一引擎实例还是反复构建：
   ```powershell
   Select-String -Path "<repo>\headroom\transforms\kompress_zh_compressor.py" -Pattern "TransformersEngine|infer_engine|global|_engine|cache|lru" -Context 1,1
   ```
2. 对照实验「原生 Swift 路径 vs proxy Transform 路径」压同一块：
   - 原生：直接用 ms-swift 官方推理 API（`swift.infer_engine.TransformersEngine` 的标准用法，主线程同步、与 AutoDL 一致）压该块计时；
   - proxy 路径：经 `_run_compression_in_executor` 在 executor 里调同一引擎压该块计时（即 H9 的 B 分支）。
3. 比较两者耗时/是否卡死，并记录引擎实例是否被跨请求复用。

**预期结果与判读**：
- 若**原生 Swift 同步路径正常、proxy Transform/executor 路径卡死**，且二者唯一差异是「执行上下文（主线程同步 vs executor 线程被反复调用）」→ **证实 H10**：根因是 Swift 引擎未被干净隔离适配进 proxy 的异步多线程模型。修复方向：把引擎放进**固定常驻 worker 线程/独立子进程**串行处理，或做成独立推理微服务（见 §6 修复方向）。

### H11 — Swift 引擎对执行上下文有隐含假设，被 proxy 每请求丢进临时 executor 破坏

**假设描述**：ms-swift 的 Swift 推理引擎对执行上下文有隐含假设（主线程 / 单进程 / 自管 CUDA stream）；proxy 每请求把它丢进临时 executor 线程反复调 → 违反假设 → 卡死。与 H9 同现象，但归因更具体到「上下文假设被破坏」。（对应 §10 H11，直接指向修复方向）

1. **「固定常驻单线程」对照**：把引擎初始化与所有压缩调用都固定在**同一个**长驻后台线程里（引擎在该线程内构建、所有请求串行投递给它），对比「每请求新建 executor 线程」：
   ```powershell
   # 伪代码思路（在临时脚本里实现）：
   # 起一个 worker 线程 W；在 W 内构建引擎；主循环把 (text) 经 queue 投给 W，W 串行压、回结果。
   # 连压 3~5 个中文块，看是否每块都正常返回（不卡死）。
   ```
2. **CUDA 上下文/stream 观察**：压缩卡死时抓线程栈，看是否卡在 CUDA 同步/分配：

**预期结果与判读**：
- 若「固定常驻单线程串行」能稳定压完多块、而「每请求新建 executor 线程」卡死 → **证实 H11**：根因是「引擎被反复换线程调用」破坏了其单上下文/单线程假设。修复=常驻 worker 串行（与 §6 一致）。
- 若 py-spy 显示 executor 线程长期停在 CUDA 同步/分配 → 佐证 CUDA stream/上下文假设被破坏。
- 若固定常驻单线程也卡死 → **排除 H11 的「线程切换」归因**，需考虑进程级隔离（独立子进程/微服务）。

> 排查结果（2026-06-27）：H9 已证「每请求新建后台线程内构建引擎」(B') 与「asyncio+executor 反复调」都不卡死，前提（换线程调用会破坏 Swift 上下文假设）在本机不成立，故 H11 无需再单独验。
> 结论：[ ] 证实  [x] 排除（就"卡死"而言）  [ ] 部分  —— 依据：执行上下文假设未被「换线程」破坏；本机失效与线程/上下文无关，是 H6 冷加载超时。

**最终根因（经 06-27 实时复测 + 离线 prefill 扫描确认）**：**8GB 显存（RTX 4060 Laptop）扛不住 codex 实时发来的大中文工具输出单元**——存在一道「prefill 时间墙 + 显存墙」：

| 单元输入字数（warm@256） | 耗时/结果 |
|---|---|
| ≤15K 字 | 17-19s，正常压成 |
| ~20K 字 | **72s**（prefill 超线性爆炸）→ 撞超时 |
| ≥25K 字 | **CUDA out of memory** → 压缩抛异常 → 静默放行（tok_saved=0） |

机制链：codex 每轮把累积上下文整帧（实测 frame 5-9 普遍 55-95KB）发来，其中的中文工具输出单元常落在 ≥20K 字区间 → 在 8GB GPU 上 **要么 72-90s 顶满超时、要么直接 OOM**，两条路都 → 原样放行、`tok_saved=0` → dashboard kompress_zh 贡献恒为 0。

**演进澄清**：① §10 原判「线程/框架卡死(H9/H10/H11)」——**已被复现实验推翻**（裸线程/asyncio+executor 都不卡死）。② 中途结论「H6 冷加载超时」——是**真实但非最终**的因（补回预加载 + 90s 超时后**今天仍超时**，opt_ms=90024）。③ 真正的最终根因是 **H7 巨帧 prefill 墙 + OOM**，受限于 8GB 显存。这解释了三处一致性：AutoDL 4090(24GB) 不 OOM、prefill 快 → 48.9% ✓；本机 8GB → OOM/超时 → ~0 ✗；离线 harness 测小样本(几 K 字) → 墙以下 → 38.5% ✓。

**正确修复方向**（调超时是错杠杆——20K 已 72-90s、再大直接 OOM）：
1. **在 kompress_zh 调用前加可配的输入尺寸上限**（content_router.py:1521 之前），按 GPU 显存设：8GB 建议 ≤~15K 字/单元。
   - 超限策略二选一：**(a) 跳过（passthrough）**——简单、稳，但大单元不省；**(b) 分块压缩**——把大单元切成 ≤15K 字的片段分别压再拼接，能省但实现复杂、需保证锚点不被切断。
2. 已落地的两个必要补丁（保留）：`eager_load_compressors` 补回 kompress_zh 预加载（消除冷加载）；`COMPRESSION_TIMEOUT_SECONDS` 改为 `HEADROOM_COMPRESSION_TIMEOUT_SECONDS` 可配。
3. `is_kompress_zh_available()` / OOM 捕获：OOM 已被 `except Exception` 兜住放行，但建议显式记日志并 `torch.cuda.empty_cache()`，避免后续请求受残留显存影响。
4. **不需要**为「卡死」做常驻 worker/子进程隔离（H9/H10/H11 已排除）。

**复测验收标准**：实时 `headroom wrap codex` 下，对中文 `function_call_output`，proxy.log 该 request_id 出现 `tok_saved>0`、`opt_ms` 为真实推理时间（非顶满超时）、**无** `forwarding original: TimeoutError`、**无** `CUDA out of memory`；dashboard kompress_zh 贡献 > 0。
**注**：本机 8GB 即便加尺寸上限，也只能压「≤15K 字的中文单元」；codex 大上下文里的超大单元在本机注定只能跳过。要完整复现 AutoDL 48.9% 仍需大显存 GPU。

**附：今天实时复测的副发现**：codex 实际走的是 **route=chatgpt_subscription / wss://chatgpt.com/backend-api/codex（ChatGPT OAuth 免费订阅）**，**没有用** 你设的 `OPENAI_API_KEY`/yunwu.ai——这解释了「额度用免费账号、key 没生效」。

### ✅ 06-27 三次复盘：API 路由打通 + 真因收敛为「功耗/热受限 GPU 压缩超时」

**API 路由打通（一串配置坑，与 headroom 代码无关）**：
1. **codex 默认走 ChatGPT OAuth**（`route=chatgpt_subscription`/`wss://chatgpt.com`），不用 `OPENAI_API_KEY`/yunwu。需 `codex logout` 切 API key 模式。

3. proxy 上游变量是 **`OPENAI_API_URL`（非 `OPENAI_BASE_URL`）**；不设则默认 `api.openai.com`，yunwu key 被 OpenAI 拒（401 invalid_api_key、带 cf-ray）。设 `OPENAI_API_URL=https://yunwu.ai`（会自动补 `/v1/responses`）。

→ 修好后 **API 路由通**：`auth_mode=payg`、连 yunwu、请求 000002（46KB、无大中文单元）秒过、gpt-5.4 正常回答。

**真因（最终）**：API 路由通后，**一旦中文 `function_call_output` 进入上下文，HTTP `/v1/responses` 压缩在本机 90s 超时** → 返回 **413 compression_refused** → codex 陷入重试死循环。逐层证据：
- 抓帧拆解：该请求 64KB，12 个 input 单元里**只有 item[11]（C3.md，4545 字中文）**符合压缩条件（仅 `function_call_output` 且 ≥512B 才压；其余英文或过小）。**只压这一个单元**。
- 该单元离线 warm **16s** 就压成（省 3862）——本不该超 90s。
- **但耗时不稳定**：同一 4.5K 字单元，离线复测从 **16s 漂到 33s**；`nvidia-smi` 证实 **SW Power Cap 降频**（笔记本 4060 功耗墙，SM 2250/3105MHz）。一整轮持续推理把 GPU 烤热/降频后，耗时翻倍；在更满负载的实时 proxy 进程里突破 90s。
- 排除项：非卡死（H9-11 已证）、非路由（API 路由已通、单元确实进了 kompress_zh）、非冷加载（预加载生效）、非 OOM/巨帧（单元仅 4.5K 字）。

**结论**：本机实时失效 = **功耗/热受限的 8GB 笔记本 GPU 压一个中等中文单元的耗时不稳定且会突破超时**。这与「kompress_zh 本体没问题、AutoDL 4090 能跑通 48.9%」完全自洽——就是这台笔记本 GPU 太弱/降频。

**立刻可用的缓解**：
- `HEADROOM_WS_FAIL_OPEN_ON_COMPRESSION_FAILURE=1`：超时改为**放行原文**（passthrough）而非 413 → **codex 不再死循环、能正常用**（只是大单元不压）。
- `HEADROOM_KOMPRESS_ZH_MAX_NEW_TOKENS=128`：减小 decode 预算 → 推理更快、更可能卡进超时。
- 笔记本插电 + 设「最高性能」电源模式 → 减轻 SW Power Cap 降频。
- 真正稳定的中文实时压缩仍建议 **AutoDL 4090**；本机适合离线 harness 评测。

## ★★★ 终极真根因（06-27 py-spy 实锤，推翻以上全部阶段性结论）★★★

> 以上「功耗/热降频」「巨帧」「冷加载」「卡死」全部是**被同一个挂起现象误导**的中间猜测。用 py-spy dump 实时挂起的 proxy 线程栈，一锤定音。

**py-spy 抓到的卡点栈**（proxy 挂满超时那 60s）：
```
Thread headroom-openai-unit_0:
  _compress_and_store → _compress_routed_unit → compress_unit_with_router
    → content_router.compress (content_router.py:968)
      → _detect_content (content_router.py:159)
        → headroom._core.detect_content_type   ← 卡在这里（Rust 预编译核心）
```

**根因**：**Windows 预编译的 Rust 核心 `headroom/_core.pyd` 的 `detect_content_type` 无条件无限挂起**——
- 独立单线程、任意输入（连 `"hello"`、单字 `"中"`）调用 `rd(...)` **100s 都不返回**（实测）。
- 它位于文本压缩单元的**必经路径**：`router.compress() → _detect_content() → Rust detect_content_type()`。
- 因此每个 ≥512B 的 `function_call_output` 单元都卡死 → 60/90s 超时 → 放行原文 → **kompress_zh 永远跑不到**（所以 GPU 永远 0%、budget 无关、风扇是 CPU/native 在转）。
- `tool_schema_compaction` 不经 `_detect_content` → 所以它正常（恒省 ~39/109）、codex 能出答案、dashboard 恒 1.3%。
- 我历次**离线测试都直接调 `KompressZhCompressor().compress()`、绕过了 router 的 `_detect_content`** → 所以从没复现，误以为是 GPU/线程问题。
- **AutoDL 能跑通**正因其 `HEADROOM_REQUIRE_RUST_CORE=false`（Python-first 检测）**天然绕开**了这个坏掉的 Rust 检测。
